# Context-size bug test: Qwen3.8-Flash-Next and Laguna-S-2.1, Nathanw fork vs upstream llama.cpp

Planned 2026-10-11; decisions settled 2026-10-13. Phase 2 built locally
2026-10-14; phase 1 (read-only build check) done 2026-10-14. No model test
has run on Framework yet.

2026-10-13 correction (found while building the harness): the first
version sized S3 at ~24k and S5 at ~18k tokens and Part B at 85% fill,
which with the 16,384-token answer budget doesn't fit 32k (or, for Part B,
32k–96k). The budget stays (D4); the prompts were shortened and Part B now
fills to `--ctx-size` − 16,384 − 2,048 with its own log, needles moved to
the same relative depths. See the fit rule under "The prompts" and Part B.

## Goal

Find **build bugs** and **context-size bugs**, not rank the models. We're
looking for:

| Bug | What it looks like |
|---|---|
| Hallucination | A fact the prompt gave, answered wrong; a fact the prompt didn't give, invented; a record id that doesn't exist |
| Repetition | The same sentence, line or n-gram again and again in the answer or the reasoning |
| Looping | Generation that never ends: hits `max_tokens`, reasoning never closes, a periodic tail, or hidden control tokens (Laguna on the fork: token 14 `〈|`) |
| Loss of instruction following | Format, length or system-prompt rules followed in a short prompt and dropped in a long one, or dropped at a bigger `--ctx-size` |

Each finding is attributed to **one** cause by changing one thing at a time:

- **Build:** same GGUF, same prompt, same settings, same `--ctx-size`; only
  the llama.cpp build differs.
- **Context size:** same GGUF, same build, same prompt; only `--ctx-size`
  differs. With an identical prompt and greedy sampling the output should
  be identical at every context size. Any difference is a bug (KV
  allocation, flash-attention tiling, RoPE/YaRN scaling chosen from
  `n_ctx`, ...).
- **Context fill** (part B): the prompt grows with the context size. Here a
  drop with length is expected to some extent (model limit); a drop on one
  build only is a build bug.

### Known state going in

- **Laguna on the fork is already known broken** (docs/model-params/README.md,
  2026-10-09): b10814 generated 465 of 476 tokens as control token 14, which
  the server hides, so it looked like empty answers and runaway "thinking".
  That's why the catalogue offers Laguna on upstream and HIP only. The four
  Laguna × nathanw cells are kept on purpose: they show whether it is still
  broken on the build under test, and whether it depends on context size.
  If the first greedy request shows the token flood, those cells run the
  short form (greedy only, see "Runs per cell").
- **Laguna scored 75.5% BFCL on llama.cpp vs 92.75% on Ollama** (2026-09).
  Tool calling isn't in this test.
- **Qwen3.8-Flash-Next's chat template defaults to `reasoning_effort=xhigh`**
  (docs/cyberseceval-panel/README.md); answers can run 12k–24k tokens of
  reasoning. See decision D4.
- **Vulkan ring timeouts at 65–80k tokens** were seen on this hardware with
  Llama-3.3-70B at default batch sizes (docs/framework-ubuntu/plan.md;
  ggml-org/llama.cpp#21724, #20515). The catalogue doesn't set
  `--batch-size`/`--ubatch-size`. This test keeps the defaults (what
  production runs) and records any `amdgpu` ring timeout as a finding;
  see D5.

## The prompts

All prompts are generated by one script from a fixed seed and written to
`prompts/` with their SHA-256 in `prompts/manifest.json`. The texts are
synthetic (made-up hosts, tickets and values), so a model can't answer from
training data and every answer is checkable by script. No downloads.

### Part A: identical prompts in every cell (S1–S5)

The same bytes are sent to all 16 cells. **Fit rule:** prompt tokens +
16,384 (the answer budget) + 2,048 (margin) ≤ `--ctx-size`, in the loaded
model's own tokens. At 32k that leaves at most 14,336 prompt tokens, so
S1–S5 are written to stay at or below ~12k in both tokenizers. Before a
cell runs, the harness checks every prompt with the loaded server's
`/tokenize` and refuses the cell if any prompt breaks the rule.

| Id | Size | What it is | Checked by script |
|---|---|---|---|
| S1 sanity | ~100 tokens | Three arithmetic/lookup questions, "answer with only the numbers, comma-separated" | exact answer; nothing but the answer |
| S2 instructions | ~400 tokens | One task with 8 verifiable constraints: a JSON object with exactly the keys `title`, `steps`, `risk`; `steps` has exactly 5 items of ≤ 12 words; no word "very"; `risk` one of `low/medium/high`; last line of the reply is `END` | each constraint pass/fail |
| S3 long-doc QA | ~12k tokens | System rule: "Start every answer with `[LOG-QA]`. Answer only from the log. If the log doesn't say, answer `NOT IN LOG`." A synthetic ops log of ~200 records (id, host, severity, ticket, value). 8 questions: 5 needles at 5/25/50/75/95% depth, 2 about things not in the log, 1 count (critical records for one host). Answer as a JSON list | prefix; each needle exact; absents must be `NOT IN LOG`; count exact; every record id cited exists |
| S4 long output | ~300 tokens in, up to ~6k out | "Write a runbook with exactly 12 numbered sections, each with a different title, 150–250 words each, no sentence repeated, end with `-- END OF RUNBOOK --`" | 12 sections in order; distinct titles; word counts; repeated sentences; end marker |
| S5 multi-turn | ~12k tokens | A scripted 8-turn conversation (fixed assistant turns). Turn 1 sets two rules: "never use bullet points" and "end every reply with `ref: TCK-4471`". The last user turn asks a question about turn 3's content | both rules on the final reply; the answer matches turn 3 |

### Part B: context fill (F)

S3's template with the same log-only/prefix rules and the first 7 questions
(5 needles and 2 absent facts), answered as a seven-item JSON list,
over its own log, as long as the fit rule allows: `--ctx-size` − 16,384 −
2,048, in the loaded model's own tokens. That is 14,336 / 47,104 / 79,872 /
112,640 tokens (about 44%, 72%, 81% and 86% of 32k / 64k / 96k / 131k).

- **The log:** filler records from one fixed seed, generated until the
  target length. F does **not** reuse S3's records; F is about depth and
  length, and the context-size comparison on identical bytes is Part A's
  job.
- **Needles:** the same five needle records as S3 (same ids and values, so
  the expected answers don't change), placed at 5/25/50/75/95% of F's own
  log, i.e. their positions move with the length. Their filler must not
  contain anything that answers the two absent-fact questions.
- **D8 (2026-10-14):** the count question is removed from F only; S3 keeps
  all 8 questions and its count. The original pilot used 8-question F
  prompts, so its F results are not comparable with later 7-question F
  results. Reports use each saved prompt's expected-answer count.
- **Same bytes per model:** the two builds of one model get identical F
  prompts at each size (one tokenizer); the two models' prompts differ in
  length. Each generated F prompt, its SHA-256, needle positions, expected
  answers and token count are written to the run's `prompts/` and
  `run.json`.

## Runs per cell

| Run | Sampling | Count |
|---|---|---|
| Greedy | `temperature 0`, `seed 1` | 1 per prompt |
| Sampled | model's recommended sampling (D3), seeds 1, 2, 3 | 3 per prompt |

- S1–S5: 4 runs each = 20 requests. F: 1 greedy + 1 sampled = 2.
- Every request: `max_tokens 16384`, `cache_prompt: false` (no prompt cache
  carried between runs, so every run is the same computation), streaming
  off, sampling sent in the request (server defaults don't matter).
- **Short form** (Laguna × nathanw if the first greedy S1 shows the token
  flood): greedy only, S1–S5 and F, 6 requests, `max_tokens 2048`.

## Detectors

All deterministic, run on every response, written to `results.jsonl` with
the raw response. Reasoning and answer are checked separately.

| Flag | Rule |
|---|---|
| `runaway` | `finish_reason == "length"` |
| `loop` | the last 2000 characters contain a ≥ 50-character string repeated ≥ 3 times back to back |
| `repetition` | any 8-word shingle appears ≥ 4 times (S4's numbered headings excluded), or zlib ratio of the last 4000 characters < 0.20 |
| `hidden-tokens` | `usage.completion_tokens` > 1.5 × the server's `/tokenize` count of reasoning + answer, and more than 100 tokens apart (the Laguna token-14 case) |
| `template-leak` | `〈|`, `<|im_end|>`, `<|im_start|>`, `<think>` or `</think>` in the answer |
| `no-answer` | empty answer with non-empty reasoning |
| `if-fail:<rule>` | any S2/S3/S4/S5 instruction check fails |
| `wrong:<q>` | a needle or count answered wrong |
| `hallucination:<q>` | an absent-fact question answered with a value instead of `NOT IN LOG`, or a record id that isn't in the log |
| `ctx-divergence` | greedy answer differs from the same build's greedy answer at 32k for an S1–S5 prompt (records the first differing character) |
| `build-divergence` | greedy answers differ between the two builds at the same size (information, not a bug by itself: the fork's kernels differ) |
| `crash` | request error, `/health` not 200 afterwards, or llama-server restarted |
| `gpu-error` | new `amdgpu` lines in `dmesg` during the request (`ring .* timeout`, `wedged`, `reset`) |

Also per request: prompt and generated token counts, prompt and generation
tok/s (from `timings`), wall time. Per cell: `/props` (`build_info`,
`n_ctx`, alias), llama-server's log from llama-swap.

**Calling a finding:**
- **Build bug:** a flag on ≥ 2 of 3 sampled seeds (or greedy) on one build
  and on 0 of 3 on the other, same model and size.
- **Context-size bug:** a flag on S1–S5 that appears only at the larger
  sizes on the same build, or any `ctx-divergence`.
- **Fill degradation:** F accuracy falling with length on both builds is
  recorded as the model's long-context limit, not a bug.
- Everything else is noise until it reproduces: re-run that one cell with
  three more seeds before reporting it.

An optional second pass sends S4/S5 answers, with the build and size hidden,
to a cloud judge for hallucinations the scripts can't see (made-up facts
in free text), the way `docs/framework-ubuntu/benchmarks.md` did its
morning judging.

## How it runs

**Harness:** `scripts/framework-ctx-bugs/ctx_bugs.py`, run on Framework as a
detached systemd user unit, the same way as `scripts/framework-ai-benchmark`
(`run-overnight.sh`). It:

1. takes `framework:run-lock` in cse-panel's Redis (job id
   `ctx-bugs-<timestamp>`, suite `ctx-bugs`), using a copy of
   `terraform/lxc/ansible/files/framework-lock/framework_lock.py`, so the eval
   battery and CyberSecEval wait and `llama-builds swap-config` refuses;
2. for each cell, loads the entry through llama-swap
   (`GET :8099/upstream/<entry>/health`), then checks `:8080/props`:
   alias is the entry id, `n_ctx` is the expected size, `build_info` is the
   expected build; it stops if any differ;
3. runs the prompts in a fixed order, checkpointing after every request
   (a restart resumes at the next request);
4. at the end reloads the model that was loaded when the run started
   (`glm-5.3-flash-upstream`, the boot default, if none was; ctx-03) and
   releases the lock, also on failure.

Results: `/storage/artifacts/framework-ctx-bugs/<timestamp>/` with
`run.json` (builds, entries, prompt hashes, settings), `results.jsonl`,
`raw/<cell>/<prompt>-<run>.json`, `logs/`, `dmesg.txt`, and `report.md`
(the flags table per cell, the divergence table, timings).

Unit tests (`test_ctx_bugs.py`, stdlib `unittest`) cover the prompt
generator (same seed → same bytes; needles where the manifest says) and
every detector with fixed positive and negative samples, including a
recorded token-14 flood.

**Catalogue entries:** the test entries are `variants` in
`ansible/00-initial-setup/files/llama-swap/models.json`, added to both
models:

```json
"variants": [
  {"suffix": "ctx32k",  "label": "ctx test 32k",  "settings": {"ctx_size": 32768,  "parallel": 1}},
  {"suffix": "ctx64k",  "label": "ctx test 64k",  "settings": {"ctx_size": 65536,  "parallel": 1}},
  {"suffix": "ctx96k",  "label": "ctx test 96k",  "settings": {"ctx_size": 98304,  "parallel": 1}},
  {"suffix": "ctx131k", "label": "ctx test 131k", "settings": {"ctx_size": 131072, "parallel": 1}}
]
```

and `laguna-s-2.1` gets `"fork"` back in `backends`, with
`"status": {"nathanw": {"status": "broken", "reason": "control token 14 flood on b10814; under test", "checked": "2026-10-09"}, ...}`
so llm-control keeps saying it's broken. Entry ids then read
`qwen3.8-flash-next-q4-nathanw-ctx32k`, `laguna-s-2.1-upstream-ctx131k`, ...
The id is the server's `--alias`, so every raw response records its cell.
(The HIP backend gets the same variants as a side effect; they aren't used.)

## Phases

### Phase 2 implementation notes (2026-10-14)

Local validation passed after review fixes: 33 unittest tests (including
interrupted-request resume, journal failures and report-table column counts),
identical prompt regeneration, and the complete 16-cell stand-in
matrix. Its 288 completed requests flag every canned bug in its expected
cell and leave all 259 clean responses unflagged. This is harness validation,
not evidence about the real models or Framework.

- Prompt counts include the chat template: `/apply-template` renders the
  messages before `/tokenize` counts them. The fit gate keeps the full
  16,384-token reserve even when running a short-form cell.
- Kernel logs use `sudo -n journalctl -k` bounded to each request's start
  and end epochs; only that window is appended once to `dmesg.txt`. GPU
  detection reads the window directly. Capture failures are retained in
  `evidence_error` and do not abort completions. Cell logs use the system
  `llama-swap.service` journal via `sudo -n journalctl`; capture errors are
  written to the cell log without aborting the run.
- The real `/props` field names were confirmed in ctx-01; ctx-07 writes
  them into the builds JSON.
- Laguna's published recommendation was confirmed from Poolside's
  [pinned sampling guidance](https://huggingface.co/poolside/Laguna-S-2.1-FP8/blob/2bea609ec5cc284a99471d3eba1e33fa9cede712/README.md):
  temperature 0.7 and top_p 0.95. top_k 20 and min_p 0 come from the
  [base checkpoint's shipped config](https://huggingface.co/poolside/Laguna-S-2.1/blob/main/generation_config.json).
  Sources and settings are recorded in `run.json`.
- A normal-budget Laguna fork S1 greedy request that triggers short form
  is saved separately as `S1-probe.json`; the six short-form requests then
  all use 2,048 tokens. If the probe is clean, it counts as the ordinary
  S1 greedy request. This preserves the 22/6-request cell layouts.
- Phase 1 must supply explicit build expectations (`name`, full `sha`,
  expected `/props` `build_info`) to `--builds-json`. The harness checks
  local `current/build.json` names/SHAs and every loaded server's props;
  it does not guess a server identity from compiler-version text.
- F uses deterministic complete records plus short inert padding to reach
  its exact rendered token target. Saved F bytes are reused across builds;
  a changed hash or tokenizer count refuses the cell.

### Execution steps

The rest of the work is written as steps (format:
`docs/agent-design/step-packet-schema.md`) for the Codex session in the
`~/git/proxmox-homelab-ctx-bug-test` worktree to run. The operator's whole
prompt is:

> Continue docs/ctx-bug-test/plan.md.

(The older "Run the next step of docs/ctx-bug-test/plan.md." means the
same thing.) The agent then works through as many steps as it can and
stops only at one of the stop points in rule 1.

#### Rules for the agent running these steps

1. **Keep going until you need the operator.** Take the first row in the
   status table that isn't `done`, do it, record it (rule 6), then take
   the next one, and so on. Stop and report only when:
   - the next step has `approval:` set and the operator hasn't approved it
     yet in this conversation (post the preflight, rule 4);
   - the next step needs an operator decision (D-numbered) or waits for a
     detached run that isn't finished;
   - a gate failed (rule 7), or something is wrong or ambiguous (rule 2).
   When you stop, say in one or two lines what you did since the last
   stop and what you need now.
2. **Read first:** this plan, `AGENTS.md`, and every file the step names.
   If anything in the step is wrong, ambiguous or doesn't match the repo,
   stop and ask. Don't choose for the operator.
3. **Local steps** (`runs_on: local`): edit only `scope.allowed_paths`,
   run every gate, and fix until all `critical: true` gates pass.
4. **Framework or production steps** (`approval:` set): first post the
   step's preflight to the operator: target, mutating or read-only, exact
   objects, exact commands, out of scope. **If the next several steps are
   all approval steps with nothing local or no decision between them
   (e.g. ctx-10g then ctx-11), post one combined preflight covering all
   of them, in order, with each step's approval name;** one "proceed"
   then approves exactly those steps. Run nothing on Framework or
   through a `with-secrets*` wrapper until the operator answers "proceed"
   (or similar) in chat. Read-only `run.sh --status` checks of a run the
   operator already approved need no new approval; if the operator says
   to wait for a run, poll it every 10 minutes until it is complete,
   then carry on. Then run exactly the step's `commands`, using the
   step's `TASK_APPROVAL` value for wrapper commands. Afterwards report what
   changed, success or failure, and follow-ups. Framework is reached as
   `ssh steve@framework.gibbsgreatly.xyz`.
5. **Commit without the production hook.** The main checkout's
   post-commit hook reindexes docs on `pve` for every docs commit. Make a
   hooks copy without it once, then commit through it every time:
   ```bash
   H="$(git rev-parse --git-common-dir)/hooks-ctx"
   [ -d "$H" ] || { mkdir -p "$H" && cp -a "$(git rev-parse --git-common-dir)/hooks/." "$H/" && rm -f "$H/post-commit"; }
   git -c core.hooksPath="$H" commit -m "<message>"
   ```
6. **When the step is done:** set its row to `done` with the date and a
   one-line result, add any facts learned to the step's "Result" line,
   commit, and push to `origin claude/qwen-laguna-model-testing-v42x6x`.
   Put large outputs (reports, logs) under `docs/ctx-bug-test/artifacts/`
   (ignored by git), not in tracked files.
7. **A failed gate ends the step and the run of steps.** Do not run any
   later command of the step, or any later step, even one that looks
   harmless; report and stop.
8. **Never:** skip, weaken or delete a gate or test; run a full teardown;
   change any model, build, or llama-swap entry except as a step says;
   promote or roll back a llama.cpp build.
