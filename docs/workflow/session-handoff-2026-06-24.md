## Issues encountered and root causes

### 1. Inventory contamination (inventory had pve-test-vm IPs)

**What happened:** All `stacks/*/inventory.yml` files had `ansible_host` values
in the +100 range (e.g., 192.168.20.110 instead of 192.168.20.10). Running any
provision.sh stack against pve with these inventories would have targeted
pve-test-vm containers.

**Root cause:** `inventory.yml` is generated by Terraform (`local_file`
resource, not committed). The sprint's pve-test-vm Terraform run overwrote all
production inventories. See Rule 4 in `session-handoff-2026-06-23.md`.

**Fix:** `terragrunt apply` for each platform stack in the pve workspace
regenerates `inventory.yml` from the pve state without touching infrastructure.
For `netbox-stack`, Terraform returned HTTP 403 (feature flags require
root@pam); inventory was manually edited to correct pve IPs.

**Applicable rule:** Always verify `ansible_host` in affected inventories before
any production Ansible run. Check that IPs are in the base range (no +100).

### 2. Stale `.generated/traefik/` files (all Traefik routes returned 404)

**What happened:** Immediately after provision, all `https://*.lab.gibbsgreatly.xyz`
routes returned 404. The Traefik proxy had stale config from the sprint's
pve-test-vm run: routes pointed to `test.gibbsgreatly.xyz` hosts with +100
container IPs.

**Root cause:** `provision.sh` calls `reconcile_all_edge` (which regenerates
`.generated/traefik/*.yml` and pushes them to the proxy) only in the post-loop
block, **after all layers succeed**. During the platform provision, the
`netbox-stack` provision in Layer 2 failed (Terraform HTTP 403). This set
`layer_failed=true` and `exit 1` immediately — the post-loop `reconcile_all_edge`
never ran. However, Layer 2 also includes `proxy-stack`, which did succeed and
pushed whatever was in `.generated/traefik/` at that moment: the stale
pve-test-vm files.

**Timeline:**
```
Layer 2 starts
  proxy-stack succeeds → deploy-proxy-stack.yml pushes stale .generated/traefik/ → 404s begin
  netbox-stack fails (HTTP 403)
layer_failed=true → exit 1
reconcile_all_edge NEVER RUNS → stale files stay
```

**Fix:** Manually ran `reconcile-edge.py --apply` with prod env (regenerated
correct `lab.*` routes), then re-ran `deploy-proxy-stack.yml`. All routes
restored.

**Mitigation:** When a full provision exits early at a layer failure, always
check `.generated/traefik/*.yml` before investigating service issues — the
proxy config may be from a previous environment's run.

### 3. Docker login failure on pve for Harbor-dependent stacks

**What happened:** `docker login harbor.lab.gibbsgreatly.xyz` returned
`Error response from daemon: Get "https://192.168.40.10/service/token":
x509: certificate signed by unknown authority`. The `deploy-netbox-stack.yml`
and `deploy-authentik-stack.yml` provisions would fail at the docker login step,
preventing `docker compose pull` from fetching updated images.

**Root cause:** Harbor on pve uses
`external_url: https://harbor.lab.gibbsgreatly.xyz`. Harbor's nginx uses this
scheme in the `WWW-Authenticate: Bearer realm=...` header it returns to Docker.
When Docker tries to get a bearer token, it calls
`https://192.168.40.10/service/token` — HTTPS at the container IP, but port 443
is closed on the Harbor container (only port 80). Additionally, Docker clients
don't trust Traefik's LE **staging** cert (`(STAGING) Dastardly Durum YR1`),
so even login via the FQDN fails without manual trust configuration.

**Workaround (in main):** Added `ignore_errors: true` and
`register: <stack>_docker_login` to the docker login task in both playbooks.
Made `docker compose pull` conditional on login success (skips pull if login
failed, uses cached images instead).

**Resolution (2026-06-24):** Two fixes applied in the same session:

1. `deploy-proxy-stack.yml` (`8188b22`): `caServer` made conditional on
   `proxy_lab_domain` — uses LE production CA when `LAB_DOMAIN` is
   `lab.gibbsgreatly.xyz`, staging elsewhere. `acme.json` cleared, Traefik
   restarted; 6 LE production certs obtained (`CN=YR2`, trusted by default OS
   trust store, expires 2026-09-21).

2. `deploy-authentik-stack.yml` and `deploy-netbox-stack.yml` (`c438882`):
   `registry_host` on pve now resolves to `LAB_FQDN_HARBOR`
   (`harbor.lab.gibbsgreatly.xyz`) via Traefik with trusted LE cert. The
   `insecure-registries` entry still uses the IP so TLS verification is not
   suppressed for the FQDN. Both stacks re-provisioned on pve; services verified
   in browser.

### 4. Portainer environments missing after provision

**What happened:** After all stacks were provisioned, Portainer showed only the
`local` environment. All five docker platform hosts
(authentik/harbor/monitoring/netbox/proxy) were missing.

**Root cause:** The `portainer_api` Ansible role (which registers a host as a
Portainer environment via the Portainer HTTP API) is called from
`deploy-portainer-agent.yml`. However, the platform stack playbooks
(`deploy-authentik-stack.yml`, etc.) do **not** call `portainer_api`. And
`provision.sh` did not call any environment registration step after provisioning.

When `portainer-stack` is re-provisioned, Portainer's Docker volume is reset,
clearing all environment registrations. Agents were running on all five hosts
(the systemd unit is pre-installed in the template), but nothing re-registered
them.

**Immediate fix:** Called the Portainer HTTP API directly to register all five
environments (IDs 2–6, all status=1/active).

**Root cause fix (commit `5366b9b`):**
- New flag `register_portainer_env: true` in `stack.yaml` for the five docker
  platform stacks.
- New lightweight playbook `register-portainer-env.yml` (only calls
  `portainer_api` role — no docker base setup).
- New `register_portainer_environments()` function in `provision.sh`, called
  after `reconcile_all_edge` in the post-loop block.

On the next full provision, all five environments will be automatically
re-registered after all layers complete.

**Remaining gap:** Single-stack mode (`--stack portainer-stack`) skips the
post-loop block. If portainer-stack is re-provisioned in isolation, environments
will be lost again until the next full provision or manual API call. The
immediate fix (direct API call) is the workaround for this case.

## Next: pve-test-vm work

Before starting pve-test-vm work, verify the following pre-conditions:

**1. Check `certs/homelab-root.crt` fingerprint (Rule 6)**

Any pve-test-vm rebuild overwrites this file with pve-test-vm's root CA. If the
fingerprint doesn't match pve's step-ca, restore it before any pve provisioning:

```bash
# Check current cert
openssl x509 -noout -fingerprint -in certs/homelab-root.crt

# Compare against pve step-ca (expected: C1:D1:77:26:...)
curl -sk "https://192.168.20.11/roots.pem" | openssl x509 -noout -fingerprint

# Restore if needed
curl -sk "https://192.168.20.11/roots.pem" > certs/homelab-root.crt
```

**2. After any pve-test-vm Terraform apply, regenerate pve inventories**

Verify that `stacks/*/inventory.yml` files still have base-range IPs after any
pve-test-vm Terraform run. If contaminated, run `terragrunt apply` per stack
in the pve workspace to regenerate.

**3. Check `.generated/traefik/*.yml` before any proxy-stack provision**

Confirm routes use `lab.gibbsgreatly.xyz` and base-range IPs. If they show
`test.gibbsgreatly.xyz` or +100 IPs, run `reconcile-edge.py --apply` with
prod env first.
