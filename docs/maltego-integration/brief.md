# Local AI + Maltego OSINT Integration

## Purpose

Develop a design and implementation plan for integrating a local open-weight AI deep research agent with Maltego for cybersecurity and OSINT investigations.

The existing environment uses a Deep Research Agent architecture based on ideas/code from Donato Capitella, with local open-weight models rather than hosted commercial AI.

The intention is **not** to build around Maltego Enterprise.

The solution must work with the free Maltego offering and should avoid dependency on paid Maltego data services wherever possible.

The architecture should favour:

- local AI
- self-hosted components
- free/open OSINT sources
- free API tiers where practical
- headless backend services
- reproducible investigations
- caching to conserve API quotas
- evidence provenance
- separation between collected facts and AI-generated hypotheses

---

# Key Design Decision

Maltego Desktop should **not** be the research backend.

Instead, Maltego should primarily act as:

- an interactive graph viewer
- an analyst investigation interface
- a way to manually initiate further investigation
- a way to inspect graph output generated by the research agent

The actual research system should run independently of Maltego Desktop.

This means that Maltego does **not** need to be running for autonomous research, API queries, enrichment, graph construction, or AI reasoning.

---

# Proposed High-Level Architecture

The initial target architecture is a hybrid of two approaches.

## Mode 1 — Autonomous Agent Investigation

The Deep Research Agent performs an investigation headlessly.

Example:

```text
User request
    |
    v
Deep Research Agent
    |
    +---- DNS
    +---- RDAP
    +---- Certificate Transparency
    +---- urlscan
    +---- VirusTotal
    +---- GitHub
    +---- Shodan / InternetDB
    +---- RIPE/BGP
    +---- Wayback
    +---- OTX
    +---- other OSINT sources
    |
    v
Investigation graph / evidence store
    |
    v
MTGX graph generation
    |
    v
Maltego Desktop
```

Maltego is not involved while the research takes place.

At the end of the investigation the system should be able to produce:

- a written research report
- structured evidence
- a relationship graph
- an `.mtgx` file that can be opened in Maltego

---

## Mode 2 — Analyst-Driven Investigation from Maltego

The analyst can use Maltego Desktop interactively.

A custom Maltego transform should be able to send an entity to the research backend.

Example:

```text
Maltego Desktop
      |
      | right-click domain/IP/etc.
      |
      v
Custom Transform
      |
      | HTTP/API
      |
      v
Research Service
      |
      +---- Deep Research Agent
      +---- OSINT services
      +---- local LLM
      |
      v
Entities + relationships
      |
      v
Maltego graph
```

An eventual user experience might therefore include transforms such as:

```text
Investigate with Local AI
Expand Infrastructure
Find Related Domains
Investigate Certificate
Investigate IP
Find Historical Infrastructure
Find Threat Intelligence
Suggest Next Pivots
```

The Maltego transform should be thin.

It should **not** contain API credentials or significant investigation logic.

Its job should mostly be:

```text
Maltego Entity
      |
      v
HTTP request to backend
      |
      v
structured results
      |
      v
Maltego entities
```

# Deployment Model

The main backend should be independent of the desktop environment.

Preferred platform:

```text
Proxmox
   |
   +---- LXC: OSINT / Research Service
```

The backend LXC should be completely headless.

There is no requirement to run Maltego in the LXC.

Maltego Graph Desktop can instead be installed on a normal desktop machine and used only when graph analysis is required.

Example:

```text
                       Framework Desktop
                     +--------------------+
                     | llama.cpp          |
                     | local AI model     |
                     +---------+----------+
                               |

                          |
```

# Maltego MCP

Investigate using `maltego-mcp` as part of the implementation.

A project already exists which exposes Maltego-related graph operations through MCP and can generate `.mtgx` files without requiring Maltego Desktop to be running.

Evaluate whether this can provide:

- graph creation
- entity creation
- relationship creation
- graph export
- MTGX generation
- useful basic OSINT enrichment

Do not assume that `maltego-mcp` should become the entire OSINT backend.

The preferred model is:

```text
Deep Research Agent
        |
        +------ OSINT MCP/API services
        |
        +------ Maltego MCP
                    |
                    v
                 .mtgx
```

Maltego MCP should primarily provide graph interoperability.

# OSINT Service Layer

A central design objective is to avoid coupling every data source directly to Maltego.

Create a shared OSINT service layer.

Conceptually:

```text
                 Deep Research Agent
                         |
                         |
Maltego Transform -------+------> OSINT Service
                         |
CLI tools ----------------+
                         |
                         v

```

Provider adapters may include:

```text
ripe

wayback
otx
```

Both the AI agent and Maltego transforms should use the same service.

# Free Maltego Constraints

The design must account for limitations of the free Maltego edition.

Do not rely heavily on:

- Maltego commercial data credits
- paid Transform Hub integrations
- Enterprise infrastructure
- commercial transform servers

Where Maltego limits the number of results returned by a transform, the backend should maintain the complete data and selectively expose the most useful relationships.

For example:

```text
crt.sh
  |
  | finds 500 records
  v
OSINT backend
  |
  +---- retain all 500
  |
  +---- analyse / rank / cluster
  |
  v
return 20 useful entities to Maltego
```

The analyst can subsequently request additional results.

---

# Caching

Caching should be a first-class service.

The same query should not repeatedly consume free API quotas.

Example cache policy:

```text
DNS                  short TTL
RDAP                 long TTL
Certificate data     long TTL
VirusTotal           medium TTL
urlscan              medium TTL
GitHub               short/medium TTL
Shodan               medium TTL
OTX                  medium TTL
RIPE/BGP             medium/long TTL
```

Exact TTLs should be configurable per provider.

The cache should retain raw provider responses wherever practical.

# Evidence and Provenance

This is especially important because an LLM will participate in investigations.

Every graph edge and significant observation should have provenance.

Example representation:

```yaml
subject: example.com
predicate: resolves_to
object: 192.0.2.10

evidence:
  provider: dns
  collected_at: 2026-10-02T10:00:00+13:00

classification: observed
```

Relationships should be classified at minimum as:

```text
observed
derived
hypothesized
```

## Observed

Directly returned by an authoritative or external source.

Example:

```text
DNS A record says:

example.com -> 192.0.2.10
```

## Derived

Deterministically inferred from evidence.

Example:

```text
Two domains share the same certificate fingerprint.
```

## Hypothesized

An interpretation generated by an analyst or AI.

Example:

```text
These domains may belong to the same infrastructure cluster.
```

A hypothesis must never silently become an observed relationship.

# Investigation Storage

Do not make `.mtgx` the authoritative investigation datastore.

Maintain an independent investigation structure.

Possible starting layout:

```text
investigations/
  case-001/
    metadata.json
    observations.jsonl
    relationships.jsonl
    hypotheses.jsonl
    sources/
    cache/
    report.md
    graph.json
    graph.mtgx
```

A database may eventually replace or supplement this structure.

Evaluate:

- SQLite
- PostgreSQL
- graph databases

Do not introduce a graph database solely because the system produces graphs.

Start simple unless there is a clear benefit.

# Longer-Term Architecture — Shared Graph Memory

Do not implement this in the first version, but account for it in the design.

A future architecture could make the investigation graph part of the Deep Research Agent's persistent working memory.

Instead of repeatedly passing research reports through the LLM context:

```text
Agent
 |
 v
structured investigation graph
 |
 +---- observed facts
 +---- sources
 +---- relationships
 +---- hypotheses
 +---- unresolved questions
```

Sub-agents could query only relevant graph portions.

For example:

```text
Find domains associated with certificates
also observed on infrastructure in ASN 12345.
```

This could reduce context usage significantly during large investigations.

Maltego would then become one possible UI onto the same underlying investigation graph.

Treat this as a later phase.

# Security Model

Because this is a cybersecurity research environment, API credentials should remain on the backend.

Do not store credentials in:

- Maltego graphs
- `.mtgx` files
- source-controlled configuration
- desktop transform definitions

Use an appropriate secrets mechanism.

At minimum:

```text
environment variables / protected config
```

Potentially later integrate with the wider secrets-management solution used in the lab.

The Maltego desktop should preferably only know:

```text
research-service URL
authentication credential for research-service
```

rather than every upstream provider credential.

---

# Network Model

The initial environment will be LAN-only.

Example:

```text
Maltego Desktop
      |
      | HTTPS
      v
osint-agent.lab.internal
      |
      +---- AI inference
      |
      +---- OSINT APIs
```

There should be no requirement to expose the research service publicly.

Add authentication even for LAN operation.

---

# Local AI

Inference is provided by an existing local AI environment, likely via an OpenAI-compatible llama.cpp endpoint.

The research backend should not tightly couple itself to one model.

Use an abstraction such as:

```text
LLM_PROVIDER=openai-compatible
LLM_BASE_URL=http://framework:port/v1
LLM_MODEL=<model>
```

The agent should be capable of using different local models for evaluation.

# Development Philosophy

Build this incrementally.

Avoid attempting to implement the complete architecture at once.

A sensible progression is:

## Phase 1 — Minimum graph proof-of-concept

Goal:

```text
domain
  |
  v
DNS + RDAP + crt.sh
  |
  v
graph
  |
  v
MTGX
```

Demonstrate that the headless backend can generate a graph which Maltego Desktop opens correctly.

---

## Phase 2 — OSINT service

Introduce common provider interfaces:

```text
lookup(entity)
```

with:

- caching
- provenance
- error handling
- rate limits

Add several free providers.

---

## Phase 3 — Research agent

Allow the Deep Research Agent to call those OSINT services.

Example request:

```text
Investigate example.com and identify associated infrastructure.
```

The agent should decide which pivots are worth pursuing.

---

## Phase 4 — Interactive Maltego transform

Create the first thin transform:

```text
Investigate with Local AI
```

The transform sends the selected entity to the backend.

---

## Phase 5 — Investigation persistence

Persist:

- observations
- edges
- provider responses
- hypotheses
- agent actions
- sources

---

## Phase 6 — Expanded providers

Add additional free/free-tier sources based on usefulness rather than quantity.

The first end-to-end experiment should remain deliberately small.

Input:

```text
example domain
```

Backend actions:

```text

RDAP
crt.sh
RIPE/ASN enrichment
```

Output:

```text
Domain
 |
 +--- resolves_to ---> IP
 |
 +--- has_nameserver ---> Domain
 |
 +--- certificate ---> Certificate
 |
 +--- SAN ---> Domain
 |
 +--- hosted_in ---> ASN
 |
 +--- registered_to ---> Organisation
```

Generate:

```text
investigation.json
report.md
investigation.mtgx
```

Open `investigation.mtgx` manually in Maltego Desktop.

This establishes whether Maltego adds enough value before more extensive development is undertaken.

# Questions the Design Phase Should Resolve

Before implementation, investigate and document:

1. How `maltego-mcp` actually constructs MTGX files.

2. Whether its graph model is sufficient for the intended relationships.

3. Whether it should be used directly or merely studied/reused.

4. What mechanisms exist for invoking an HTTP-backed custom Transform from current free Maltego Desktop.

5. What limitations current Maltego Basic imposes on custom/local transforms.

6. Which free OSINT providers have usable APIs as of the current date.

7. Rate limits and licence restrictions for each provider.

8. Appropriate common entity types.

For example:

```text
Domain
IPAddress
ASN
Netblock
Certificate
URL
EmailAddress
Organisation
Person
Repository
FileHash
Technology
ThreatActor
Malware
Vulnerability
```

9. Appropriate relationship vocabulary.

10. A common provider interface.

11. Investigation storage format.

12. Authentication between Maltego Desktop and the backend.

13. How provider failures and quota exhaustion should be handled.

14. How AI-generated hypotheses should be visibly differentiated from evidence-backed graph edges.

# What Claude Code Should Produce Next

Do **not** immediately implement the whole system.

First produce a technical design based on this brief.

The design should contain:

- architecture
- components
- interfaces
- data flows
- deployment model
- entity model
- evidence/provenance model
- investigation storage
- API design
- caching strategy
- secrets handling
- Maltego integration mechanism
- MCP integration
- local-model integration
- logging and observability
- testing strategy
- identified unknowns
- risks and trade-offs

Then produce a staged implementation plan.

The plan should break work into small, independently testable milestones.

For each milestone provide:

- objective
- components affected
- implementation tasks
- tests
- completion criteria

Do not optimise prematurely.

The primary first milestone is simply:

> A headless service accepts a domain, performs several free OSINT queries, constructs a provenance-aware relationship graph, generates an MTGX file, and that graph opens successfully in free Maltego Desktop.

Everything else should build from that.
