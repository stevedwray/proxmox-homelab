# T-Pot event panels in Grafana, read from the central OpenSearch

Status (2026-10-15): **planned, nothing built.** Follows `monitoring-plan.md`
(host health/metrics, deployed) and the cAdvisor dashboard
`terraform/lxc/stacks/monitoring-stack/dashboards/tpot-honeypot.json`.

## Why Grafana, not OpenSearch Dashboards

`docs/opensearch-stack/README.md` (operator decision 2026-09-02) abandoned
hand-writing OpenSearch Dashboards saved objects: no rendering feedback, stale
saved-object cache, version-sensitive viz schema. Grafana is the chosen front
end (`docs/threat-vuln-platform/plan.md` Phase 10).

## Data path

```
T-Pot Logstash -> T-Pot internal ES (Pi, localhost:64298)
   -> tpot-findings-ingest.timer (hourly, on secpipe-stack, SSH tunnel)
   -> central OpenSearch (opensearch-stack) index tpot-events-YYYY.MM.DD
   -> Grafana (monitoring-stack) via a read-only OpenSearch user
```

Up to ~1 h behind live. Grafana reaches OpenSearch :9200 already (MikroTik rule
`monitoring-stack: mgmt_seg to opensearch-stack opensearch 9200`).

## Facts verified 2026-10-15

- Central `tpot-events-*`: ~223k docs / ~23 MB per day, daily indices from
  2026.09.30 (+ `tpot-events-sync-state`). No index template: dynamic mapping,
  identical to the source. `src_ip`, `dest_ip`, `honeypot`, `alert.signature`,
  `geoip.country_name` are `text` with a `.keyword` subfield; `@timestamp` is
  `date`; `dest_port` is `long`. Use `.keyword` for terms aggregations.
- Content is almost all noise, not attacks (T-Pot's own ES, 10-10..10-15,
  1.15M events): `type` = Suricata 1,146,350 / P0f 2,396 / NGINX 4 -- **no
  Cowrie/Dionaea/etc. events at all**. 1,133,455 alerts (99%) are
  `SURICATA Ethertype unknown`. Sources are LAN hosts (the Pi, the NAS,
  secpipe, link-local IPv6). Real signal is small: ET INFO reserved-internal
  traffic (2.7k), OpenSSH CVE-2024-6387 banner (296), SSH sessions (130).
  Meaning: the honeypot sees no internet traffic, so panels would show LAN
  activity unless that changes.
- The existing Grafana->OpenSearch pattern is an exporter + Infinity
  datasource scoped to `uvm_dashboard_reader` (role limited to three index
  patterns, user `uvm_dashboard_exporter`, credential generated by the
  playbook into `/…/uvm-dashboard-exporter/es-user.env`).

## Proposed changes (monitoring-stack only)

1. `deploy-monitoring-stack.yml`: add role `tpot_events_reader` (read on
   `tpot-events-*` only) and user `grafana_tpot_events`, generated password
   written to a 0600 env file, same idempotent "only if credential file
   missing" shape as the uvm-dashboard user. Never the admin user.
2. Grafana container: append `grafana-opensearch-datasource` to
   `GF_INSTALL_PLUGINS` (same mechanism as the Infinity plugin) and pass the
   password via the existing `.env` file.
3. Datasource provisioning: add an OpenSearch datasource,
   `index: tpot-events-*`, `timeField: @timestamp`, `version: 2.19.x`,
   `tlsSkipVerify: true` (matches `uvm_dashboard_es_no_verify_tls`).
4. New dashboard `tpot-events.json`: events over time by `honeypot.keyword`;
   alerts excluding the Ethertype noise by `alert.signature.keyword`; top
   source IPs split LAN/external; destination ports; event types; external
   source countries; a "noise share" stat.
5. Before loading, each panel's query is run against the central index (read
   only) and the result checked, as was done for the cAdvisor dashboard.

## Decisions needed from the operator

- **Exposure:** keep T-Pot LAN-only (panels = LAN visibility), or expose it
  (port-forward/DMZ) for real attack data? Not a code change, and not mine to
  make.
- **Noise:** drop `SURICATA Ethertype unknown` at the source (Suricata/Logstash
  filter on the Pi -- touches `~/tpotce/`, off-limits by the management
  boundary) or only filter it in Grafana queries (recommended: no host change).
- **Retention:** ~23 MB/day is small; no ILM exists for `tpot-events-*`.
  Decide whether to add a retention policy later.

## Operator actions (agents have no OpenBao/OpenSearch write access)

None are expected for steps 1-4 (the playbook creates the OpenSearch user with
the admin credential it already reads from OpenBao, as the uvm user is). The
deploy itself is `scripts/provision.sh --stack monitoring-stack` under the
production approval flow.
