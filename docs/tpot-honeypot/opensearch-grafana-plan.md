# T-Pot event panels in Grafana, read from the central OpenSearch

Status (2026-10-15): **built and committed, NOT deployed** (see "Implementation" at the end). Follows `monitoring-plan.md`
(host health/metrics, deployed) and the cAdvisor dashboard
`terraform/lxc/stacks/monitoring-stack/dashboards/tpot-honeypot.json`.

## Why Grafana, not OpenSearch Dashboards

`docs/opensearch-stack/README.md` (operator decision 2026-09-02) abandoned
hand-writing OpenSearch Dashboards saved objects: no rendering feedback, stale
saved-object cache, version-sensitive viz schema. Grafana is the chosen front
end (`docs/threat-vuln-platform/plan.md` Phase 10).

## Data path

```
T-Pot Logstash -> T-Pot internal ES (Pi, localhost:64298)
   -> tpot-findings-ingest.timer (hourly, on secpipe-stack, SSH tunnel)
   -> central OpenSearch (opensearch-stack) index tpot-events-YYYY.MM.DD
   -> Grafana (monitoring-stack) via a read-only OpenSearch user
```

Up to ~1 h behind live. Grafana reaches OpenSearch :9200 already (MikroTik rule
`monitoring-stack: mgmt_seg to opensearch-stack opensearch 9200`).

## Facts verified 2026-10-15

- Central `tpot-events-*`: ~223k docs / ~23 MB per day, daily indices from
  2026.09.30 (+ `tpot-events-sync-state`). No index template: dynamic mapping,
  identical to the source. `src_ip`, `dest_ip`, `honeypot`, `alert.signature`,
  `geoip.country_name` are `text` with a `.keyword` subfield; `@timestamp` is
  `date`; `dest_port` is `long`. Use `.keyword` for terms aggregations.
- Content is almost all noise, not attacks (T-Pot's own ES, 10-10..10-15,
  1.15M events): `type` = Suricata 1,146,350 / P0f 2,396 / NGINX 4 -- **no
  Cowrie/Dionaea/etc. events at all**. 1,133,455 alerts (99%) are
  `SURICATA Ethertype unknown`. Sources are LAN hosts (the Pi, the NAS,
  secpipe, link-local IPv6). Real signal is small: ET INFO reserved-internal
  traffic (2.7k), OpenSSH CVE-2024-6387 banner (296), SSH sessions (130).
  Meaning: the honeypot sees no internet traffic, so panels would show LAN
  activity unless that changes.
- The existing Grafana->OpenSearch pattern is an exporter + Infinity
  datasource scoped to `uvm_dashboard_reader` (role limited to three index
  patterns, user `uvm_dashboard_exporter`, credential generated by the
  playbook into `/…/uvm-dashboard-exporter/es-user.env`).

## Proposed changes (monitoring-stack only)

1. `deploy-monitoring-stack.yml`: add role `tpot_events_reader` (read on
   `tpot-events-*` only) and user `grafana_tpot_events`, generated password
   written to a 0600 env file, same idempotent "only if credential file
   missing" shape as the uvm-dashboard user. Never the admin user.
2. Grafana container: append `grafana-opensearch-datasource` to
   `GF_INSTALL_PLUGINS` (same mechanism as the Infinity plugin) and pass the
   password via the existing `.env` file.
3. Datasource provisioning: add an OpenSearch datasource,
   `index: tpot-events-*`, `timeField: @timestamp`, `version: 2.19.x`,
   `tlsSkipVerify: true` (matches `uvm_dashboard_es_no_verify_tls`).
4. New dashboard `tpot-events.json`: events over time by `honeypot.keyword`;
   alerts excluding the Ethertype noise by `alert.signature.keyword`; top
   source IPs split LAN/external; destination ports; event types; external
   source countries; a "noise share" stat.
5. Before loading, each panel's query is run against the central index (read
   only) and the result checked, as was done for the cAdvisor dashboard.

## Operator decisions (2026-10-15)

- **Purpose:** the honeypot is an internal tripwire -- detect someone who has
  got onto the LAN. It stays LAN-only. The dashboard is therefore built around
  "anything unexpected touching the Pi", not attack statistics.
- **Noise:** filter the obvious false positives in the Grafana queries, not on
  the Pi (no change under `~/tpotce/`). Initial exclusions: `SURICATA
  Ethertype unknown`, `ET INFO Reserved Internal IP Traffic`, the SURICATA
  STREAM reassembly/ack/FIN/retransmission decode alerts, DHCP/DHCPv6/NetBIOS.
- **Retention:** deferred (~23 MB/day).

## Finding that must be resolved before the dashboard means anything

In 15 days of data (9.9M events) the only event `type`s are Suricata, P0f and
NGINX. **No honeypot sensor (Cowrie, Dionaea, Mailoney, Heralding, Tanner,
...) has ever logged a single event** -- not even when Greenbone probed
:21/:22/:23/:25/:80 on the Pi. Either those sensors are not reachable on
those ports, or their logs are not reaching Logstash. Until a deliberate test
connection to a honeypot port from the LAN produces a sensor event (in T-Pot's
ES and then in `tpot-events-*`), the tripwire is unproven and a quiet
dashboard is not evidence of a quiet LAN.

## Implementation (2026-10-15, branch work/tpot-monitoring)

- `deploy-monitoring-stack.yml`: role `tpot_events_reader` (cluster
  `cluster_composite_ops_ro`, index `read` on `tpot-events-*` only), user
  `grafana_tpot_events` with a generated password kept in
  `<monitoring_compose_dir>/grafana/tpot-events-es.env` (0600, created once,
  re-read into the Grafana `.env` as `TPOT_EVENTS_ES_PASSWORD` every run);
  `GF_INSTALL_PLUGINS` gains `grafana-opensearch-datasource`; a provisioned
  datasource `T-Pot Events` (uid `tpot-events`, `tpot-events-*`, TLS skip-verify
  like the uvm exporter). The password-extraction Jinja expression was tested
  for present/empty/no-match credential files.
- Dashboard `terraform/lxc/stacks/monitoring-stack/dashboards/tpot-events.json`
  (generated; 17 panels): tripwire row (sensor events, from unexpected sources,
  distinct sources, filtered Suricata alerts, latest unexpected events table),
  network-context row (filtered Suricata alerts/signatures/sources/ports/
  countries) and a sensor-coverage text panel. All 6 distinct Lucene queries
  were validated against T-Pot's own ES (24h): they parse and the counts are
  sensible (58 sensor events, all from the Kali test host).
- Allowlist = the `NOT src_ip.keyword:(...)` clause in the tripwire queries
  (Pi itself, .1.4, garuda .1.104, router .1.251, secpipe, monitoring, Graylog,
  Technitium, Wazuh, Greenbone). Edit the generator/JSON to change it.

## Update 2026-10-24: tripwire alert, source-address finding, sync cadence

- **The dashboard's "from UNEXPECTED sources" panels are misleading.** The sensor documents carry Docker
  bridge addresses as `src_ip` for LAN-originated connections (Cowrie `192.168.112.1`, Dionaea `172.29.0.1`,
  Honeytrap `172.24.0.2`), so every Greenbone sweep counts as an unexpected source and the allowlist can
  never match. Rebuild those panels on the Suricata-flow query below. Not done yet.
- **The query the alert uses** (Suricata sees the wire, so `src_ip` is the real client): `honeypot:suricata AND
  event_type:flow AND dest_ip:"192.168.1.28" AND NOT dest_port:<management and broadcast ports> AND NOT
  src_ip:<allowlist> AND dest_port:[1 TO 32767] AND src_port:[1024 TO 65535]`. The two port ranges keep only
  inbound connections: the reverse shape (source port 443 or 53, ephemeral destination) is the Pi's own outbound
  traffic seen mid-stream. 30 days: 81 flows, all from the Kali test host on 2026-10-15; 7 days: none.
- **The sensor-coverage finding above is resolved:** sensors now log (17 events in 7 days, one Greenbone sweep).
- **Sync cadence:** `tpot_findings_ingest_on_calendar` is now every 10 minutes (was hourly; a oneshot unit with
  a stored cursor, so runs cannot overlap), so the alert's worst-case delay is about 12 minutes.
- The alert and its routing are in `docs/alerting/` (rule file `homelab-honeypot.yml`, Phase 1c in its plan).
