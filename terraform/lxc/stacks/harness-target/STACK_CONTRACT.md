# harness-target — Stack Contract

## Purpose

a small, dedicated, always-repeatable target for an automated PentAGI test harness. Deliberately separate from Metasploitable2 (too large, too iconic/recognizable to the model from training data, and its known vulnerabilities aren't reliably re-runnable without a VM reset). This target is exactly two non-trivial services, neither inviting password brute-forcing (Struts2's RCE needs no credentials at all; Redis has no auth mechanism to guess), both producing clear evidence on success (Struts2: command execution output; Redis: a seeded marker key), and neither ever requiring a reset between test runs (Struts2's exploit is a stateless per-request OGNL injection; Redis is configured with zero persistence so it is self-resetting by construction on every container start).

## What Must Not Be Edited Casually

The Redis command-line flags (--protected-mode no --save "" --appendonly no, given as a compose `command:` list, not a shell string, to avoid YAML quote-escaping bugs) are load-bearing for this stack's entire purpose (unauthenticated + stateless) -- do not "helpfully" add persistence or auth.

## Playbook

`deploy-harness-target`

This stack is deployed with `lxc_base` + `docker_base` roles plus a docker-compose file, with a task that seeds a Redis marker key (internal:api_key) via `docker exec ... redis-cli SET` after every `docker compose up` -- this must run unconditionally on every deploy (idempotent -- the same SET every time) since the Redis container itself never persists data across restarts.
